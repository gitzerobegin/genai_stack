# Stage 0: Architecture hypotheses H1–H8 and the evidence each needs

Verdicts are given in Stage C. Stage A collects the evidence listed here. The verdict options are **keep / rename / merge / split / reposition**.

| # | Hypothesis | Evidence Stage A must collect | Stream |
|---|---|---|---|
| H1 | Split L2 into **model serving → inference optimisation → model gateway/routing**, and promote the gateway to the control plane | <ul><li>Do serving engines (vLLM, SGLang), managed inference clouds and routers (OpenRouter, LiteLLM, Portkey, cloud AI gateways) now market themselves as distinct categories?</li><li>Gateway features: policy, quotas, logging, guardrail hooks</li><li>Separate optimisation tooling (speculative decoding, quantisation, KV-cache, LMCache, NVIDIA Dynamo, llm-d)</li></ul> | ④, ⑥ |
| H2 | An agent framework is not one layer. **Deterministic workflows** should be distinguished from **autonomous agents**. | <ul><li>How LangGraph, Microsoft Agent Framework (workflows vs agents), the OpenAI Agents SDK, the Claude Agent SDK, Pydantic AI (graph) and CrewAI (Flows vs Crews) separate the two</li><li>Durable-execution integrations (Temporal, DBOS, Restate)</li><li>Vendor guidance on "workflows vs agents"</li></ul> | ④ |
| H3 | Tools and protocols need an **agent identity, authorisation and tool-governance** sub-layer | <ul><li>MCP authorisation spec (OAuth 2.1, resource indicators)</li><li>MCP registry and governance</li><li>A2A security model</li><li>Microsoft Entra Agent ID, Okta/Auth0 for AI agents, SPIFFE for agents</li><li>MCP gateways</li><li>OWASP agentic threats</li></ul> | ③, ⑥ |
| H4 | **Memory** may not be separate from retrieval and data architecture | <ul><li>How Mem0, Zep, Letta, Cognee, Supermemory and LangMem store memory (vector + graph + KV)</li><li>Their underlying stores</li><li>Built-in model-vendor memory (e.g. Claude/OpenAI memory tools)</li><li>Erasure/retention features</li></ul> | ③ |
| H5 | "Vector database" should become **Retrieval / Knowledge Stores** | <ul><li>Hybrid (BM25 + vector) and full-text support across stores</li><li>Vector features in general-purpose databases (Postgres, MongoDB, Elastic, OpenSearch, Oracle, SQL Server)</li><li>Object-store vectors (S3 Vectors)</li><li>Vendor repositioning, e.g. "search engine" or "knowledge platform"</li></ul> | ② |
| H6 | Embeddings and reranking form one **retrieval-optimisation** layer | <ul><li>Vendors shipping both embed and rerank (Cohere, Voyage, Jina, NVIDIA, Qwen3)</li><li>Late-interaction (ColBERT/ColPali), contextualised chunk embeddings</li><li>Rerank inside vector DBs (Pinecone, Elastic)</li></ul> | ② |
| H7 | Ingestion must include **lineage, classification, PII/DLP, access-control metadata and incremental indexing** | <ul><li>Enterprise features of Unstructured, Reducto, LlamaParse/LlamaCloud and Docling (permissions sync, connectors, PII)</li><li>Lineage standards (OpenLineage)</li><li>DLP integration patterns</li></ul> | ①, ⑥, ⑦ |
| H8 | Evaluation and observability are **cross-cutting**, not a downstream layer | <ul><li>OpenTelemetry GenAI semantic conventions status</li><li>Eval-in-CI features</li><li>Online evaluation and guardrail coupling</li><li>Regulatory expectations for ongoing monitoring (SR 11-7, PRA SS1/23, EU AI Act post-market monitoring)</li></ul> | ①, ⑧ |
